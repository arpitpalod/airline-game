# airline-game

Multiplayer airline business game for office colleagues. Read `docs/SPEC.md` before any work; it is the source of truth for rules, numbers and architecture.

- Owner works phone-only (no laptop). Every build, deploy and test step must run from a Claude session or a hosted service.
- Back end: Supabase (own project, Mumbai region). Front end: installable React web app on GitHub Pages.
- The repo is public. Never commit secrets or service keys.
- All game rules run server-side. The app never writes tables directly.
- Numbers marked (G) in the spec are tunable game values; keep them in data tables, not in code.

## Working notes

- Database changes reach the live database through `.github/workflows/db.yml` (spec 14.9): add a new file to `supabase/migrations`, open a PR, and when the owner merges it the workflow applies every file not yet in `game.applied_files`, each in one transaction. Merging is the approval, so say plainly in the PR what a migration changes. Never edit a migration that is already applied; add a new one. The workflow uses the repository secret `SUPABASE_DB_URL` (Session pooler connection string, set 19 Nov 2026; a password reset in Supabase means updating it). It can be re-run with `gh api -X POST repos/arpitpalod/airline-game/actions/workflows/db.yml/dispatches -f ref=main`.
- Do not apply migrations through the Supabase tool: its approval prompt for anything that looks destructive never reaches the owner's phone (three tries timed out on 19 Nov 2026), and the workflow would then try to apply the file again. Use the Supabase tools for reads and for rolled-back checks.
- After the workflow runs, compare the `md5(prosrc)` list it prints with the local test database.
- Live end-to-end check that leaves nothing behind: run the actions and `game.run_day` inside one `do` block that ends with `raise exception` carrying the results. The error returns the numbers and the whole block rolls back.
- Local test: `tools/pgtest/` runs all migrations in an in-memory Postgres, then 181 pass/fail checks (`node run.mjs ../../supabase/migrations`, add `--perf` for the 50-airline load test; about a minute). The engine checks switch the random parts off through `game_params` so results are exact. Checks written before 0013 run in worlds without pilots (`run.mjs` sets the default); `checks_5.mjs` covers pilots, `checks_6.mjs` the computer-run airline changes of 0016. `tools/calibrate.py` is the reference market model; its numbers must match the database.
- Season simulation: `node season.mjs ../../supabase/migrations` plays a full season (2,366 game days, about 15 minutes) with the computer-run airlines and 18 simulated players using 9 strategies, and prints yearly results, unit costs, slot use, trunk fares and the pilot market. `--pilots off` runs without pilots; places default to one per simulated player. Use it to re-check tuning after changing game values.
- Callers with no user id (service role, the scheduler, the computer-run airlines) may act for any airline; signed-in players only for their own. The computer-run airlines act through the same public action functions, called from the engine.
- App: `app/` (React, TypeScript, Vite; HashRouter, so links look like `.../#/route/<id>`). The Supabase URL and publishable key in `app/.env.production` are public by design. Reads go straight to tables under row-level security; every change goes through a public function.
- App test: `sh tools/localstack/run_e2e.sh` (needs `npm install` in `tools/localstack` and `app`; about 2 minutes). It uses the local Postgres 16 in `/usr/lib/postgresql/16` and the Playwright browsers in the session. The shim supports only the PostgREST features the app uses (plain column lists, eq/neq/gt/gte/lt/lte/in/is, order, limit): keep app queries within them, or extend the shim.
- Airport coordinates come from OurAirports (`airports.csv`, downloaded per session, not committed).
